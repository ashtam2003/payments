What Is Authorize.net?
1
Authorize.net — The Middleman
Authorize.net Dashboard — main interface for account management and transactions

Authorize.Net is a platform owned by Visa Inc. that acts as a middleman between your website/app and the financial institutions involved in a transaction. It handles the entire technical bridge — from capturing card data to routing it through banks and returning a result.

🔌 What It Allows You To Do

  • Accept credit cards & debit cards
  • Process digital payments online
  • Handle recurring / subscription billing
  • Manage fraud protection
  • Accept eChecks (ACH payments in the US)
  • Support digital wallets (Apple Pay, Google Pay)
  • Send digital invoices via email links

🏛️ Key Facts

  • Founded: 1996
  • Owner: Visa Inc.
  • One of the oldest and most trusted gateways
  • Processes millions of transactions daily
  • Serves businesses of all sizes
  • Supports websites, mobile apps, POS systems
Gateway vs Processor — Key Distinction

Authorize.net is the gateway — it captures, encrypts, and forwards your transaction. The processor / acquiring bank is the entity that actually controls approvals and your merchant account. When things go wrong, both need to be checked.

Customer Initiates PaymentA customer enters card details on your website/app checkout page.
2
Data EncryptionSensitive card data is encrypted using SSL before any transmission occurs. Raw card data never travels in plain text.
3
Gateway ProcessingAuthorize.Net receives the encrypted transaction and forwards it to the payment processor.
4
Card Network RoutingThe request goes through the appropriate card network — Visa, Mastercard, AmEx — routing to the customer's issuing bank.
5
Issuing Bank ApprovalThe customer's bank checks: available balance, fraud indicators, card validity. Then approves or declines the transaction.
6
Response BackThe result (approved/declined + response code) is returned through the network back to your site — almost instantly (~2 seconds).
7
SettlementApproved transactions are batched and settled into your merchant bank account — usually within 1–3 business days.
✅ Approval Path

Customer → SSL encrypt → Authorize.net → Processor → Card Network → Issuing Bank → Approved → Auth code returned → Capture → Settlement → Merchant receives funds

❌ Decline Path

Same path, but issuing bank (or fraud filter) returns a decline code. Transaction stops. Hold is released. Customer told payment failed. No money moves.

Sample API Request — Charge a Card
→
Request JSON — authCaptureTransaction
{
  "createTransactionRequest": {

    // Authentication — who you are
    "merchantAuthentication": {
      "name": "YOUR_API_LOGIN_ID",
      "transactionKey": "YOUR_TRANSACTION_KEY"
    },

    // Transaction details
    "transactionRequest": {
      "transactionType": "authCaptureTransaction",  // Auth + Capture = Sale
      "amount": "10.00",

      // Payment method — credit card
      "payment": {
        "creditCard": {
          "cardNumber": "4111111111111111",   // Test card number
          "expirationDate": "2026-12",           // Format: YYYY-MM
          "cardCode": "123"                      // CVV
        }
      }
    }
  }
}
🔑 Required Fields Always

name = your API Login ID
transactionKey = your Transaction Key
transactionType = what kind of transaction
amount = dollar amount as string

📅 Date Format Note

Expiration date uses YYYY-MM format (e.g., 2026-12 for Dec 2026). Not MM/YY as printed on card. This is a common integration mistake.

Detailed Credential Information
🆔 API Login ID

On the API Credentials & Keys page, you will see your API Login ID displayed. This is a unique identifier for your merchant account. It's already visible on this page and does not require any action to generate — it's always there. Example: 233Loc9Jy9u

🔑 Transaction Key

The Transaction Key is a critical authentication credential used for API calls. To obtain it:

Steps to Generate or Retrieve:
  1. Select "New Transaction Key" from the API Credentials page. Click this button to generate a new key.
  2. Click Submit. The system will prompt you to verify your identity for security.
  3. For security, you will be prompted to request and enter a PIN that is sent to your registered email address. Check your email for this PIN.
  4. After entering the PIN correctly, the new Transaction Key will be displayed on the screen.
  5. ⚠️ Copy it immediately — it will NOT be shown again for security reasons. Once you navigate away from this page, you cannot retrieve the same key again. If you lose it, you must generate a new one.

The Transaction Key is what you use alongside your API Login ID for every server-side API request. Keep it private and secure — treat it like a password.

✍️ Signature Key (For Webhooks/IPNs)

The Signature Key is used to validate webhook (Instant Payment Notification) payloads sent from Authorize.net to your server:

How to Get It:
  • Look for "Signature Key" section on the API Credentials page.
  • If you already have one, it will be displayed (usually masked with asterisks for security).
  • If you don't have one, click "Generate New Signature Key" button to create one.

This key is essential for Server Integration Method (SIM) and webhook validation. It ensures that notifications you receive are genuinely from Authorize.net and haven't been tampered with.

🌐 Public Client Key (For Accept.js)

The Public Client Key is used for client-side tokenization via Accept.js (Authorize.net's frontend library):

Steps to Get It:
  1. Go back to the Account tab if you're not already there (Account > Account and API Settings > Security Settings).
  2. Under Security Settings, click "Manage Public Client Key".
  3. If one hasn't been created yet, you will be prompted to answer a security question to generate a new Public Client Key.
  4. Once generated, the key will be displayed and is safe to use in your frontend/browser JavaScript code (it's intentionally public).

The Public Client Key is designed to be used safely in browser-side JavaScript with Accept.js. It can tokenize card data on the client side before it reaches your server, providing an extra layer of security. Unlike the Transaction Key, it's safe to expose.

API Credential Dates and Audit Trail

On the API Credentials & Keys page, you will also see:

  • API Login ID last obtained: The date and time when this credential was last generated or accessed. This helps track account activity.
  • Transaction key last obtained: The date and time when your current Transaction Key was generated. This helps you track credential age and security updates. If you see an unexpected date, your key may have been regenerated without your knowledge.
🚨 Security Best Practices for Credentials

Never expose your API Login ID, Transaction Key, or Signature Key in browser-side JavaScript, client code, or public repositories (GitHub, GitLab, etc.). These must be stored securely on your backend server only. The only credential safe for frontend use is the Public Client Key. Rotate your Transaction Key periodically (at least every 6–12 months) and immediately if you suspect compromise.

💡 Credential Management Tips

Save securely: Use environment variables or a secure secrets manager (e.g., AWS Secrets Manager, HashiCorp Vault, Azure Key Vault) to store credentials, never hardcoded. Separate by environment: Keep sandbox credentials separate from production credentials. Log access: Track when credentials were last used to detect unauthorized access. Regenerate regularly: Even if there's no breach, rotate credentials every 6–12 months as a best practice.

⚠️ If You Suspect Credential Compromise

1. Immediately go to the API Credentials page — click "New Transaction Key" to generate a fresh key. The old key will be invalidated. 2. Update your application code with the new Transaction Key. Any API calls using the old key will start failing. 3. Check your transaction logs for any suspicious activity during the suspected compromise period. 4. Contact Authorize.net support if you see fraudulent transactions made with your account.

AFDS
Advanced Fraud Detection Suite
A configurable, rules-based system that evaluates every transaction before authorization.
Fraud Detection Filters Dashboard — configure and manage transaction filters

The Advanced Fraud Detection Suite (AFDS) is a configurable, rules-based system that evaluates every transaction before it is forwarded for bank authorization. Merchants can set filters to automatically approve, decline, or hold transactions for manual review.

→
Fraud Filters Available

⚡ Velocity Filters

Limits on how many transactions can occur in a time window. Blocks rapid-fire attempts — a common fraud signal. Example: max 5 transactions per IP per hour.

💵 Amount Filters

Set minimum and maximum allowed transaction amounts. Large unusual transactions (e.g., $13,000 when average is $50) are flagged automatically.

🌍 Geographic / IP Filters

Block or flag transactions from specific countries, regions, or IP ranges. Useful if your business only serves certain geographies.

🖥️ Suspicious Pattern Detection

Detects unusual patterns like multiple cards from the same IP, same card tested with different amounts, or mismatched BIN location vs customer IP.

🔑 CVV Mismatch Rules

Automatically decline or review transactions where the CVV does not match the issuing bank's records. Configurable strictness levels.

📮 AVS Mismatch Rules

Decline or flag when billing address or ZIP code doesn't match the card's registered address. Strict AVS settings significantly reduce fraud.

→
Three Outcomes When a Filter Triggers
✅

Approve

Transaction passes all filters. Forwarded to issuing bank for authorization as normal.

⏸️

Hold for Review

Transaction flagged but not declined. Merchant must manually approve or decline it in the dashboard.

❌

Auto-Decline

Transaction automatically rejected before it ever reaches the issuing bank. No auth attempt made.

🔧 Configuring AFDS

Access AFDS settings in the Authorize.net dashboard under Tools → Fraud Detection Suite. You can enable/disable individual filters, set thresholds, and choose the action (approve/review/decline) for each filter independently. If legitimate transactions are being declined, start here — relax filters temporarily to diagnose.

CVV Errors
CVV — Card Verification Value Codes
The issuing bank's response regarding the CVV provided.
What is CVV Verification?

The issuing bank compares the CVV submitted in the transaction against what's on file. The response is a single letter code returned in the API response. Even if the bank approves the transaction, you can choose to decline based on a bad CVV match in your AFDS settings.

CodeMeaningAction
MCVV matches — correct security code providedProceed normally
NIncorrect CVV / security code — does not matchDecline or flag for review
SCVV is required but was not providedAsk customer to re-enter CVV
UUnable to verify CVV — issuer doesn't support verificationUse other fraud signals to decide
PCVV was not processed by issuing bankTreat as unverified, apply caution

AVS Errors
AVS — Address Verification System Codes
How the billing address compares to what the bank has on file.
What is AVS?

AVS compares the billing address (street + ZIP) submitted with the transaction against the cardholder's registered address at the issuing bank. Mismatches don't always mean fraud, but they are a strong fraud signal. The response is a letter code.

CodeAddress Match?ZIP Match?Meaning
Y✅ Yes✅ YesFull match — address and ZIP both correct. Low fraud risk.
A✅ Yes❌ NoAddress matches but ZIP code does not match
Z❌ No✅ YesZIP code matches but street address does not
N❌ No❌ NoNeither address nor ZIP match — high fraud risk, consider declining
P——Address verification not supported by this card / international card
U——Address verification unavailable — issuer didn't respond
International Cards & AVS

Many non-US cards return code P or U because their issuing banks don't participate in AVS. This is expected — not a red flag on its own. Use CVV and other fraud signals for international transactions.

Decline Causes
Why Payments Suddenly Start Declining
Seven root causes — especially relevant after a large or unusual transaction.
1
Fraud Detection Filters Triggered

Authorize.net's built-in fraud tools may flag a larger-than-usual transaction and temporarily block or decline further payments. Triggers include:

Velocity filters (too many transactions quickly)Amount filters (unusually high value)IP or geographic mismatchSuspicious pattern detection
2
Merchant Account Review / Hold

Your payment processor or acquiring bank (not just Authorize.net) may flag your account. Very common for:

Unusual transaction sizeSudden spike in volumeFirst large payment on accountNew merchant accounts

Result: Account goes into review mode. New transactions get declined or held until reviewed by the processor. Remember — Authorize.net is just the gateway. The processor controls approvals.

3
AVS / CVV Mismatch Rules

If your AFDS fraud settings are strict: incorrect billing address (AVS) or wrong CVV causes auto-declines based on filter settings. Check and adjust filter strictness if legitimate customers are being declined.

4
Transaction Limits Reached

Your account may have processor-imposed limits:

Daily transaction limitMaximum per-transaction amountMonthly processing cap
5
Gateway / API Configuration Issues

Sometimes triggered after first successful payment: incorrect API credentials in subsequent calls, duplicate transaction errors, or invalid payment data. Always check error codes in API responses.

6
Chargeback / Risk Flag

If a large payment looks risky or is flagged by the card network, your account may be temporarily restricted. The processor can place a hold while they investigate.

7
Card Issuer Declines (Not Authorize.net)

Sometimes the decline comes from the customer's bank — not Authorize.net at all. Reasons: insufficient funds, international transaction blocked, bank fraud flag. These show as "declined by issuer" in the dashboard.

Real-World Scenario
What Typically Happens
The most common sequence of events when payments suddenly start declining.
📖 Scenario

Your account usually processes small payments. Suddenly a large amount comes through. Then — all further payments start declining. Here's exactly what happened.

1
Account usually processes small paymentsNormal operating pattern — small, predictable transactions. Processor and fraud systems have established a "normal" baseline.
2
Suddenly receives a large paymentA transaction significantly larger than the account's historical average comes through (e.g., $13,516 when average is $50–$200).
3
Risk system flags it as unusualEither AFDS amount filter fires, or the payment processor's own risk system sees the unusual spike. The large transaction may or may not succeed — but it raises a flag.
4
Processor puts account into temporary restrictionThe acquiring bank / processor places the merchant account into review mode. This can happen even if the original large transaction was approved.
5
All further payments declineEvery subsequent transaction gets declined at the processor level — regardless of card validity or available funds. The decline appears to come from Authorize.net but the real cause is the processor review.
6
Resolution: Contact processor directlyOnly the processor can lift the restriction. Call them, explain the business reason for the large transaction, provide documentation if needed. Review typically clears within 1–3 business days once resolved.
❌ What Doesn't Help

Retrying transactions repeatedly. Changing Authorize.net API settings. Contacting Authorize.net customer support (they can't lift a processor-level restriction). These won't resolve a processor account review.

✅ What Actually Helps

Calling your acquiring bank / processor directly. Providing business justification for the large transaction. Asking to have your transaction limits officially raised. Getting written confirmation of the review status.
